# b9候補：External MCP Readiness（設計のみ）

本書は b9 の**設計文書**である。b8 では b9 の実装・実接続は
開始しない（ブリーフ§30）。対象は、ChatGPT等の外部MCP
クライアントから Global Library MCP を安全に利用できるように
するための論点整理である。

## 目的

ローカル（stdio／ローカルStreamable HTTP）で提供してきた
read-only research プロファイル（14ツール）を、外部クライアント
経由でも同じ安全性で使えるようにする。研究ワークスペースの
保存データは外部公開しない（b7/b8 の境界を維持）。

## 論点

### 1. 外部送信の権利ポリシー
- 外部クライアントへ返すデータは「送信」である。資料の権利
  （§13の層分離）ごとに、メタデータ／抜粋／OCR本文の送信可否を
  ポリシー化する。権利不明・制限付き資料は参照情報のみ。
- プロンプトインジェクション対策として、OCR等の外部データは
  従来どおり data_notice を付け、指示として扱わせない。

### 2. 認証・認可
- Secure MCP Tunnel 等の接続方式ごとに、クライアント認証、
  利用者識別、スコープ（research プロファイル限定）を設計する。
- APIキー等の資格情報は本プロジェクトでは発行・保管しない
  方針を維持し、接続先の仕組みに委ねる範囲を明確化する。

### 3. 利用者別予算と実行制限
- 利用者／クライアント別の HTTP 予算、応答サイズ上限、実行
  期限、同時実行数を、既存の操作予算（op budget）の上に
  階層化する。予算枯渇は部分結果として返す（現行踏襲）。

### 4. 監査ログ
- 外部経由のリクエストについて、ツール名・対象機関・件数・
  予算消費を記録する。研究データ自体（ノート・保存資料）は
  ログにも外部にも出さない。

### 5. 段階導入の候補
- 候補A：トンネル経由の research プロファイル公開（読み取り
  専用、ワークスペースなし）— 既存のローカル HTTP 実績を基礎に
  最も小さい変更で外部接続する案。
- 候補B：ホスト型エンドポイント（運用主体・費用・データ
  所在地の判断が先行する案）。
- いずれも実装開始には別途承認（接続方式、公開範囲、費用、
  送信データ範囲の明示）が必要。

## b8 からの引き継ぎ事項

- DPLA／Europeana の API キーは未発行のまま。外部接続と
  キー発行は独立した承認事項として扱う。
- Finna／Digi は許可されたネットワークからの実地検証が
  未達成。到達性が変われば再検証する。
- 権利ポリシーの信頼モデル（Stage 0）は外部送信ポリシーの
  土台として再利用できる。
