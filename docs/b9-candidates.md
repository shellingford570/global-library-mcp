# b9候補：External MCP Readiness（設計のみ）

本書は b9 の**設計・調査文書**である。b8 では b9 の実装・
実接続は開始しない。対象は、ChatGPT等の外部MCPクライアント
から Global Library MCP を安全に利用できるようにするための
論点整理である（最終レビュー §33 で30課題に拡張）。

## 推奨構成

```
ChatGPT等の外部AIクライアント
  ↓ 認証・認可されたMCP接続
外部向け読み取り専用プロファイル（新規・専用）
  ↓ 資料権利・外部送信ポリシー
LibraryService
  ↓
各国図書館・デジタルアーカイブ
```

Research Workspace は独立したローカル非公開領域として
維持する。外部プロファイルからワークスペースへは到達
できない（現行の MCP がワークスペースへアクセスしない
境界を、そのまま外部にも適用する）。

## 最優先課題：外部向け専用プロファイルの必要性

現在の research プロファイルが14ツールの読み取り専用で
あることは、その応答に含まれる**すべての資料を外部AIへ
送信してよいことを意味しない**。ローカルで閲覧・保存
可能な資料と、第三者サービスへ送信可能な資料は別の
集合である。したがって外部向けには専用プロファイルを
新設し、ツール集合・応答フィールド・抜粋の上限・送信
条件を個別に定義する。research プロファイルの流用は
しない。

## 30の設計課題

### A. プロファイルと外部送信ポリシー
1. 外部向け専用プロファイル（上記）。
2. 外部送信可能なメタデータの範囲（書誌事項の層分離）。
3. 外部送信可能な原文抜粋の条件（権利カテゴリ別）。
4. OCR全文の送信制限（原則送らない。上限と例外の定義）。
5. 原本画像URLの送信条件（URL自体が送信対象である点に留意）。
6. 権利不明資料は参照情報のみ返却する。
7. 利用者による明示的同意（送信範囲ごとの同意取得と撤回）。

### B. 認証・認可
8. OAuth等の認証方式。
9. 認可スコープ（プロファイル・機関・操作の粒度）。
28. 外部接続の停止・権限失効の手順。

### C. 実行制御
10. 利用者別HTTP予算（既存の操作予算の上に階層化）。
11. 同時操作数の制限。
12. セッション分離。
13. キャッシュ分離（利用者間で応答キャッシュを共有しない）。
14. 応答サイズ上限。
15. ツール実行期限。
16. キャンセル伝播。
17. 長時間調査の分割（期限内に収まる単位への分解）。

### D. 監査と秘密情報
18. 監査ログ（ツール名・対象機関・件数・予算消費。
    研究データ自体はログにも出さない）。
19. 秘密情報保護（資格情報を応答・ログ・統計に混入
    させない。b8 の DPLA キー除去の仕組みを一般化する）。

### E. 攻撃面
20. プロンプトインジェクション対策（OCR等の外部データは
    従来どおり data_notice を付け、指示として扱わせない。
    外部クライアント側の扱いは保証できないため、送信
    データ自体の最小化が本質的な対策になる）。
21. SSRF対策の強化。
22. DNSリバインディング対策（現行は `GLM_DNS_CHECK` で
    任意有効化。外部公開時は必須化を検討）。

### F. 接続方式と互換性
23. 安全な外部MCP接続方法の選定。
24. OpenAI Secure MCP Tunnel の利用条件。
25. ChatGPT の公式接続条件（対象プラン、ワークスペース
    権限、管理者承認の要否）。
26. MCP仕様互換性（プロトコル版・トランスポート）。
27. 費用と契約条件。

### G. 境界の維持
29. 研究ワークスペース非公開の維持（上記構成のとおり）。
30. 有料LLM不要の調査モード（外部接続でも、回答生成を
    伴わない書誌・原典調査が成立する現行の性格を保つ）。

## 再確認事項（実装時点）

OpenAI の公式仕様、対象プラン、ワークスペース権限、
Secure MCP Tunnel の条件、実行期限、応答サイズ、費用等は
変動し得るため、**b9 実装時点の最新公式資料で再確認**
する。本書の記述は設計上の論点であり、現時点の公式
条件の主張ではない。

## 段階導入の候補

- 候補A：トンネル経由の外部向け専用プロファイル公開
  （読み取り専用、ワークスペースなし）— 既存のローカル
  HTTP 実績を基礎に最も小さい変更で外部接続する案。
- 候補B：ホスト型エンドポイント（運用主体・費用・データ
  所在地の判断が先行する案）。
- いずれも実装開始には別途承認（接続方式、公開範囲、
  費用、送信データ範囲の明示）が必要。

## b8 からの引き継ぎ事項

- DPLA／Europeana の API キーは未発行のまま。外部接続と
  キー発行は独立した承認事項として扱う。
- Finna／Digi は許可されたネットワークからの実地検証が
  未達成。到達性が変われば再検証する。
- 権利ポリシーの信頼モデル（b8最終レビューで閉集合化・
  復元降格・共通判定まで整備）は外部送信ポリシーの
  土台として再利用できる。ただし「ローカルで信頼できる
  観測」と「外部へ送信してよい範囲」は別の判断であり、
  信頼モデルをそのまま送信許可に流用しない。
